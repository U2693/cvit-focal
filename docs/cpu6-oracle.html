Using Meisaka's CPU6 implementation as an oracle

This document describes a differential-testing harness for biscvit. Meisaka's CPU6 implementation will be treated as a reference machine: both implementations receive the same initial state, execute one instruction, and have their resulting states compared. The purpose is to build a compatible implementation in biscvit while retaining the freedom to optimize its inner loops later.

Goals

  • Find instruction-decoding and execution differences with a reproducible test case.
  • Test one instruction at a time rather than trying to infer errors from a long OS boot.
  • Separate architectural CPU behavior from interrupts, clocks, and device behavior.
  • Use randomized initial states after the hand-written tests establish the basic semantics.

Known oracle implementation

The reference source is available on playa at:

/Users/rsbohn/build/CenturionComputer/Emulators/Meisaka/Emu 0.22/src/cen.ts

The CPU executor is UMCPU6, whose single-instruction entry point is step(). Its main state fields are mem, reg, page, _pc, cc, level, and registers. SysMem supplies the byte-level memory interface. The compiled JavaScript is also present, but the TypeScript source is the better adapter target.

This changes the first milestone from “locate the oracle” to “extract and wrap the existing CPU core.” The source is browser-oriented and includes UI globals, so it may need a small Node-compatible extraction or a purpose-built adapter. Do not make the browser application itself the protocol boundary.

The adapter must explicitly translate register and condition-code formats; it must not compare the raw cc byte to biscvit's flags byte. Meisaka's showreg(), pcfetch(), and pcfetchw() methods are useful references while building the adapter.

Execution model

initial state + instruction bytes
          | \
          |  \
          v   v
      oracle  biscvit
          |   |
          +---+--> normalized state comparison

One test step means one call to each implementation's normal single-step routine. An instruction may consume multiple bytes, so “one opcode” means one complete CPU6 instruction, not one fetched byte. The harness must capture the state immediately after that step.

Initial scope: disable interrupt delivery, clock advancement, terminal input, and device side effects. This produces a deterministic core-ISA oracle. Add those features in separate test suites once ordinary instruction behavior matches.

State to exchange

The normalized state should include every architecturally observable value:

CategoryFields
ControlPC, halted/trap/unknown-op status
RegistersAll sixteen byte registers, or the eight word pairs (AX, BX, RT, DX, EX, SP, GX, HX)
FlagsCarry, negative, zero, and interrupt-enable state
Privilege/contextCurrent IPL, interlevel registers, and any register-file bank state
MemoryChanged bytes, including writes through the active address translation
MMUPage-table contents and active map, when relevant
DevicesOnly in device-specific suites; avoid them in core-ISA tests

Memory should be represented sparsely in the external protocol. The test case supplies only initialized regions, and the response reports changed bytes. A complete memory image can still be used internally by either CPU.

Suggested JSON-lines protocol

A long-lived process avoids process-startup overhead when running thousands of cases. It reads one JSON request per line and emits one JSON response per line.

Request

{
  "op": "step",
  "events": { "interrupts": false, "clock": false, "devices": false },
  "state": {
    "pc": 256,
    "ipl": 0,
    "flags": 0,
    "regs": ["0000", "0000", "0000", "0000", "0000", "FFFE", "0000", "0000"],
    "memory": [{ "address": 256, "bytes": "50 12 34" }],
    "interlevel": []
  }
}

Response

{
  "ok": true,
  "decoded": "...",
  "state": {
    "pc": 259,
    "ipl": 0,
    "flags": 4,
    "regs": ["0000", "0000", "0000", "0000", "0000", "FFFE", "0000", "0000"],
    "writes": [{ "address": 4096, "old": 0, "new": 42 }],
    "halted": false
  }
}

The decoded field is useful diagnostic information but is not itself the compatibility criterion. The comparator should use machine state, not matching disassembly text.

biscvit integration

Add a test-facing snapshot and restore API to Cpu6, rather than scraping trace or console output:

CpuSnapshot Snapshot();
void Restore(CpuSnapshot state);

The snapshot needs access to flags, IPL, the register file, interlevel registers, memory, MMU state, and halt state. Existing public facilities such as Cpu6.Step(), PC, SetRegPair(), and Translate() can remain useful for the interactive monitor, but the differential runner should use the snapshot API for exact setup.

A biscvit oracle-server mode can then translate JSON requests into:

  1. construct or reset a CPU;
  2. restore the supplied state and instruction memory;
  3. disable external events for the core suite;
  4. call Step() once;
  5. emit the normalized post-step state and memory writes.

Test progression

  1. Protocol smoke tests: NOP, HALT, and flag set/clear instructions.
  2. Hand-written instruction cases: one representative for every opcode family and addressing mode.
  3. Boundary cases: zero, sign-bit, carry/borrow, page boundaries, stack wraparound, and unaligned/overlapping memory operations where legal.
  4. Randomized cases: random registers, flags, safe RAM contents, and legal instruction encodings.
  5. System cases: MMU operations, interlevel operations, interrupts, and devices in isolated suites.
  6. Regression corpus: retain every minimized mismatch as a permanent test.

Comparison rules

On a mismatch, report the seed, initial state, instruction bytes, oracle state, biscvit state, and the first differing field. The report should also show the disassembly and a memory diff around every changed address.

Not every field is necessarily defined by every instruction. The test harness should maintain per-instruction comparison masks for fields that are architecturally unchanged, undefined, or implementation-specific. It must not turn an unspecified result into a false failure.

Tests involving MMIO need explicit semantics for reads and writes because reads may consume input and writes may produce output. Keep those tests out of the core suite, or provide a deterministic mock-device state to both implementations.

First implementation milestone

  1. Make the Meisaka Emu 0.22/src/cen.ts source available to the adapter build and retain its upstream version identity.
  2. Extract the smallest usable subset containing UMCPU6, SysMem, register views, opcode tables, and required helpers.
  3. Provide deterministic memory callbacks and stub or disable UI, parity-break, device, and interrupt side effects.
  4. Define the normalized state format and translate Meisaka's register/condition-code representation.
  5. Add Cpu6 snapshot/restore support in biscvit.
  6. Add a persistent biscvit JSON-lines step server.
  7. Run a handful of deterministic core instructions through both adapters.
  8. Only then add randomized generation and the full opcode corpus.

The oracle should remain a development and verification dependency. The shipped biscvit emulator must not depend on it at runtime; after behavior is matched, the oracle-driven tests become a fast regression suite for future optimizations and opcode fixes.
