cvit filesystem

The cvit filesystem is the native filesystem personality used by the biscvit Hawk boot path. It is not an Apple ProDOS disk format clone. It borrows some user-facing ideas from ProDOS and CED, while using the project’s native 400-byte Hawk/Disk6 image layout.

Current on-disk layout

Hawk image: out/os.img

sector 0x0000       boot sector
sector 0x000E       control sector
sector 0x0010       volume header
sector 0x0012..17   SYSTEM UAL sectors
sector 0x0020       SYSTEM directory page 0
sector 0x0021..     SYSTEM member payload sectors

Hawk payload sector = 400 bytes
cvit library page   = 200 bytes
1 sector            = 2 cvit pages

Allocation model

ConceptCurrent behavior
Directory unit200-byte cvit page number stored in SYSTEM directory rows.
Allocation unit400-byte Hawk sector. Members are sector-aligned.
Empty file allocationEmpty files now receive one sector to avoid overlap with the next member.
GrowthNot supported yet. Writes must fit in the member’s current allocation.
CreationCED can create a fixed one-sector SYSTEM member by appending a directory row and UAL entry.
Deletion/reuseNot supported yet. Created sectors are appended; freed space is not tracked.

SYSTEM directory rows

The current SYSTEM library directory is a simple row table in sector 0x20. Each row is 16 bytes. Member names are uppercase and currently limited to 10 characters.

OffsetMeaning
0..9High-bit uppercase member name, padded with spaces.
10Low 7 bits of start page.
11Currently unused/reserved.
12High page component stored as 0x08 + page / 128.
13Current type/attribute byte, commonly 0x14.
14..15Currently unused/reserved.

The directory terminator is 84 8D. Current tooling only uses directory page 0, so there is a practical limit on the number of members until directory growth is implemented.

SYSTEM UAL

The SYSTEM UAL begins at sector 0x12. It lists the sectors making up the SYSTEM library. Current creation appends one new sector to that list and bumps the sector count stored at the start of UAL sector 0.

UAL sector 0:
  bytes 0..1   sector count minus one
  bytes 2..3   load address placeholder
  byte  4      FSI shift placeholder
  byte  5      reserved
  bytes 6..    3-byte sector entries, terminated by FF FF FF

Current implementation boundary

The emulator now has a CvitFileSystem helper class that encapsulates the current SYSTEM member operations:

  • find member
  • read text member
  • write text member
  • create fixed one-sector member
  • append sector to SYSTEM UAL
  • encode/decode directory rows

This is still a bring-up shortcut. The plan is to move these semantics behind kernel calls so programs do not depend on emulator-assisted services.

Known limitations

  • Created files are always one sector.
  • Writes larger than the current allocation fail with ?TOO BIG.
  • No delete, truncate, rename, or sector reuse yet.
  • No robust recovery if a write is interrupted midway.
  • Only a single mounted Hawk image is used even when FQFNs mention H1:.
  • Directory capacity is limited by current single-page SYSTEM directory handling.
